# M-27 — 기기 트래픽에서 "핫스팟 내부" 를 제외할 수 있는가 (조사만)

## 1. 질문

> "안드로이드 기기의 UP/DOWN 를 체크 하는데 전체 속도를 체크 하고 있는데…
> 이게 내부에서 핫스팟으로 동작 되는 것 까지 다 포함 이야.
> 실제 기기에서 외부로 나갔다가 들어 오는 용량만 체크 할 순 없는건가? 내부 트래픽은 제외 하고"

## 2. 조사 ① — 지금 세는 게 뭔가

현재 코드는 `TrafficStats.getTotalRxBytes()` / `getTotalTxBytes()` 다.
**모든 인터페이스의 합**이다. 이 기기에서 실측:

```
rx  swlan0(热点) =  1,409,487,036
rx  rmnet (외부) = 28,071,189,791
rx  total        = 29,480,756,834   ← 1.4 + 28.1 = 29.5 ✓ 정확히 맞다

tx  swlan0(热点) = 47,184,283,248   ← ★ 전체의 67%
tx  rmnet (외부) = 23,140,067,832
tx  total        = 70,324,632,272
```

> **tx 의 67% 가 핫스팟 내부 트래픽이다.** 사용자가 느낀 것이 맞았다.

## 3. 조사 ② — M-24 가 실패한 경로는 여전히 실패다

```
run-as … cat /proc/net/dev                        → Permission denied
run-as … cat /sys/class/net/swlan0/statistics/tx_bytes → Permission denied
```

**M-24 의 기록이 정확했다.** 파일 직접 읽기는 막힌다.

## 4. 조사 ③ — 그런데 숨겨진 길이 하나 있었다

`TrafficStats.getRxBytes(String iface)` — **인수에 인터페이스 이름을 받는 API** 다.
`android.jar`(일반 앱용) 에는 **없고** 시스템 jar 에만 있는 **hidden API** 다.

**리플렉션으로 불러 앱 uid 로 실측**했다 (임시 프로브 라우트 → 삭제함):

```json
{ "iface": "swlan0",      "rx": 1406689361, "tx": 47151019262 }
{ "iface": "rmnet_data2", "rx": 25509210888,"tx": 20325433870 }
{ "iface": "rmnet_ipa0",  "rx": 0,          "tx": 0 }
```

**앱 uid 로 정상값이 나온다.**

> **M-24 가 못 찾은 이유** — `adb shell` 로 테스트하면 **셸 uid** 라서 되고,
> 그게 성공한 것을 "앱도 된다"로 착각하게 된다. **앱 안에서 직접 읽어야만
> "앱이 할 수 있는가"가 답이 된다.**
>
> **SELinux 가 막는 건 파일 직접 읽기뿐**이고, `TrafficStats` 안쪽 Binder 경로는 통과한다.

## 5. 조사 ④ — rmnet 만 보면 진짜 외부 트래픽인가

3구간을 나눠 재고, 같은 크기 트래픽을 다른 경로로 흘려 **증분을 비교**했다.

| 구간 | swlan0Δtx | rmnetΔrx | totalΔtx |
|---|---|---|---|
| ① 내부만 (200회 요청) | 116,759 | 3,868,448 | 2,318,330 |
| ② **외부 25MB** | **6,619,775** | **43,890,914** | 21,406,525 |
| ③ 내부만 (200회 요청) | 1,022,106 | 5,168,953 | 2,179,866 |

②가 ①③ 대비: `swlan0Δtx` **11.6배** · `rmnetΔrx` **9.7배** · `totalΔtx` **9.5배**.

> **핫스팟 AP 경유 트래픽은 `swlan0` 과 `rmnet` 양쪽에 다 잡히지만,
> 증분이 다르다.** 그래서 **합으로 빼는 방식이 아니라 rmnet 만 읽는 방식**으로
> 구분된다. `total − swlan0` 로도 가능하지만 **뺄셈은 언제든 음수가 될 수 있다.**
> **rmnet 을 직접 읽는 게 안전하다.**

## 6. 결론

**가능하다.** `rmnet*` 인터페이스 카운터만 읽으면 "외부로 나갔다 오는 양" 이 된다.

**다만 미구현 — 이유 3가지:**

1. **hidden API** — `android.jar` 에 없다. **OEM 이 안에서 바꾸면 조용히 깨진다.**
   실패 시 **0 이 아니라 "미지원" 을 알린다** (M-24 가 세운 규칙 그대로).
2. **`rmnet*` 이름이 기기마다 다르다** — 이 기기는 `rmnet_ipa0`·`rmnet_data0~14`·`swlan0`.
   삼성/高通/mediatek 이 다르다. **하드코딩하면 다른 기기에서 0 이 된다.**
3. **프런시 설정에 없다** — "기기" 열을 "핫스팟 포함 / 외부만" 로 나눌지,
   아니면 그냥 외부만으로 바꿀지 **사용자 결정이 필요하다.**

**조사만 했다.** 임시 프로브 라우트는 삭제했고, 프로브 없는 상태로 재설치·동작 확인했다.

# M-26 — 속도 표시가 두 줄로 접혔다

## 1. 목표
사용자 스크린샷 1장. 그래프 위 속도 표시가 **두 줄로 접혔다.** 원인 확인 후
**그래프 또는 팝오버 폭을 넓혀서 깨지지 않게 고쳐라.**

**(후속)** 같은 대화에서 두 가지가 더 왔다 —
① "그래프 가로를 더 넓혔으면 하는데? 좌우 패딩을 반으로 줄여서" → **여백 12 → 6**
② "기기 UP/DOWN 이 핫스팟 내부 트래픽까지 포함한 것 같은데, **외부로 나갔다 오는 것만**
   셀 수 있나?" → **조사만 (M-27), 구현 보류**

## 2. M-26 — 원인은 37pt 부족 (PR 없음, main 직접)

### Investigated — 추정이 아니라 실측

`NSFont` 로 문자열 폭을 직접 재고, SwiftUI 에 실제로 배치해서 대조했다.

| 항목 | 값 |
|---|---|
| **실제 필요폭** | **365.0 pt** |
| 그때 가용폭 (352 − 12×2) | **328.0 pt** |
| **부족** | **−37.0 pt** |

**근본은 `lineLimit` 이었다.** SwiftUI 의 `Text` 는 **기본적으로 여러 줄을 허용**하고
폭이 모자라면 **물어보지 않고 접는다.** 한 단어가 통째로 안 들어가면 **글자 중간에서 자른다** —
그래서 `Droid` 가 `Droi` / `d` 로 갈렸다. **고장 났는데 경고가 없다.**

같은 줄의 축 라벨만 `lineLimit(1)` 이라 **잘림(`…`)** 으로 갔다.
**접힘과 잘림이 한 줄에 섞여 있었다** — 어느 쪽이 버그인지 화면만으로는 애매했다.

### Changed — 352 가 여섯 군데에 있었다

`PopoverView` 4곳 · `StatusItemController` 1곳 · `SpeedGraph` 1곳.
**한 곳을 넓혀도 나머지가 따라가지 않아 반쪽만 고쳐지는** 상태였다 —
그래서 이번엔 **`PopoverMetrics`(Core) 한 곳**에서 뺀다.

- **팝오버 352 → 450 pt** (그래프 328 → **426**). 실측 365 대비 **+17% 여유**.
- **설정 창(460)보다 좁게** — 팝오버가 더 넓으면 "작은 걸 열었더니 더 큰 게 떴다" 가 되고
  **두 창이 같은 앱의 조각으로 읽히지 않는다.**
- **접히지 않게 만드는 안전장치**: `lineLimit(1)` **+** `fixedSize(horizontal: true)`.
  **둘을 같이 써야 한다** — `lineLimit(1)` 만 주면 한 단어가 안 들어가면 그것까지 자른다.
  여백이 모자라면 **축 라벨이 양보**한다. **속도값이 축 참고치보다 먼저 사라져서는 안 된다.**

## 3. 이번 작업에서 배운 것

### ① 진단이 내 계산을 잡아 준다 — 그것이 진단의 존재 이유

`PopoverMetrics` 는 글꼴 폭을 **계수로** 재고, 테스트 13건이 **전부 통과**했다.
그 상태에서 `--legend-check`(실제 뷰를 `NSHostingView` 에 넣어 재는 진단)를 돌리니:

```
계산 필요폭  : 344.8pt
실제 필요폭  : 365.0pt      ← 20.2pt 차이
```

**`Spacer` 는 HStack 의 자식**이라 **간격을 두 번** 받고 **자체로 10pt** 를 차지하는데,
계산에는 **간격 3곳(30pt) 만** 넣고 **Spacer 를 잊었다.**

> **여전히 365 < 416 이라 화면은 멀쩡했고 아무도 몰랐다.**
> 값이 조금만 길어져 필요폭이 385 로 뛰면, **계산은 "들어간다"고 하고 실제로는 접힌다.**

**M-21 교훈("계산이 맞다 ≠ 화면에 간다")이 그대로 재현됐다.** 그리고 이번엔
**계산 쪽이 틀렸다** — 지난번처럼 적용 쪽이. **진단이 없었으면 영영 못 찾는다.**

수정 후 **계산 364.8 vs 실제 365.0 — 차이 0.2pt.**

### ② 과소평가만으로는 버그를 못 찾는다 — **과대평가만 안전하다**

폭 예산에서 **어느 방향으로 틀리느냐가 전부**다.

| 방향 | 결과 |
|---|---|
| **과대평가** | 여유가 남는다 — **안전** |
| **과소평가** | "들어간다"고 판단했는데 **접힌다** — **이게 M-26** |

게다가 **과대평가도 버그**다. "안전하려고" 폭을 과하게 잡으면 **그건 좁게 만든 것과 같고**,
계수가 글꼴에서 멀어졌다는 신호가 사라진다. → **양쪽 다 테스트로 지킨다.**

### ③ 진단도 틀렸다 — 그리고 그게 더 흥미롭다

`--legend-check` **첫 판이 "깨진다"고 했다.** 그런데 계산 364.8 < 가용 416.

원인은 판정 기준이 아니라 **판정 대상**이었다.
`SpeedGraph` 전체를 재서 **62pt** 가 나왔는데, 그건
**범례 12 + 간격 4 + `Canvas` 46** 이었다. **범례는 이미 한 줄이었다.**

→ **`SpeedLegend` 로 분리**했다. 그래프와 한 덩어리로 재면
**`Canvas` 46pt 이 항상 섞여 한 줄인지 두 줄인지 구분되지 않는다.**

> **틀린 게 계산이 아니라 재는 대상이었다.**
> "한 줄로 나온다" 를 확인하려면 **한 줄만** 재야 한다.

### ④ 글꼴 계수를 두 번 틀렸다 — 테스트가 잡았다

| 잘못한 가정 | 실측 | 고친 값 |
|---|---|---|
| 한글은 "전각 = 1.0 × 크기" | **0.865** | 0.90 (1.0 이면 15% 과대) |
| `·` `→` `↓` `↑` 는 전각 | **0.618** — ASCII 와 동일 | 반각 |

두 번째가 특히 아까웠다. **축 라벨이 `"… · 보통 …"` 이라 `·` 가 제일 자주 나오는데**
전각으로 세면 **범례가 있는 매 프레임 몇 pt 를 과대평가**하고
**"들어갈 자리가 있는데 안 들어간다" 는 거짓 진단**이 된다.

`↓` `↑` 를 시스템 폰트로 그리면 **0.796** 이라 **계수 0.55 보다 넓다** →
**과소평가 → 접힘을 놓친다.** 지금은 값·축 라벨을 **모노로** 그리고
시스템 폰트는 **출처 이름(`Droid`/`기기`) 뿐**이며 거기엔 화살표가 없다.
→ **이 사실을 테스트가 지킨다** (`test_화살표는_모노로만_그린다`).

### ⑤ 같은 색을 두 번 적으면 같은 출처가 두 개로 보인다

그래프 선과 범례 점의 색이 **각각 정의**돼 있었다. 어느 한쪽만 바꾸면
**같은 출처인데 달라 보인다** — 그리고 **어느 쪽이 맞는 색인지 알 방법이 없다.**
→ **`SpeedColor` 한 곳.**
