# 세션 로그 — 2026-09-29 (macos, M-21 설정 창 왼쪽 하단 버그)

## 1. 목표
M-20 병합 후 사용자 보고: **"설정 왼쪽 하단에 뜸, 창 다시 열면 이동된 위치에 잘 뜸."**
→ **생성 위치**가 잘못됐고, **위치 기억**은 잘 됐다는 뜻이다. 둘을 갈라 봐야 한다.

## 2. 사고 — 계산은 맞고 창은 그곳에 안 갔다

`--settings-check` 는 (670, 291) 을 찍었고 테스트도 통과했는데 **실제 창은 왼쪽 아래**였다.

| | 값 |
|---|---|
| 진단이 계산한 값 | (670, 291) |
| 실제 `w.frame` (init 직후) | **(0, -28)** |
| 사용자가 본 것 | 화면 왼쪽 하단 |

> **계산이 맞다 ≠ 창이 그곳에 간다.**
> `setFrameOrigin` 이 안 불렸거나, 불린 뒤 다른 코드가 옮겼거나 둘 중 하나다.
> **진단이 "계산값만" 찍고 "실제 창을 띄워서 `w.frame` 을 읽지" 않은 게 공백이었다.**

진단을 고쳐서 **실제 창을 띄우고** init 직후 → applyPlacement 후 → present 후를 읽게 했다.
**그러자 (0, -28) 이 그대로 나왔다.**

## 3. 원인 두 개

**① `contentRect: NSRect(x: 0, y: 0, …)`** — `y: 0` 은 화면 **아래쪽**이고 `x: 0` 은 왼쪽이다.
AppKit 좌표는 아래에서 위로 올라간다. `applyPlacement()` 로 나중에 옮기지만
**창이 뜨는 첫 순간은 이미 (0,0)** 이고 그 사이 사용자는 화면을 본다.

**② `(0, -28)` 은 더 나빴다** — `contentRect` 는 **내용물** 영역이라 위로 제목바 28pt 가 붙고
그만큼 화면 밖으로 나갔다. "왼쪽 아래"보다 나쁜 **"제목바가 화면 밖에 있다."**

→ `init` 에서 바로 가운데로 세팅. `contentSize` 를 창 크기의 유일한 출처로 모았다.

## 4. 사고 — 가운데 계산에서 28pt 어긋남 (테스트가 잡았다)

`initialContentOrigin` 을 처음엔 이렇게 적었다:

```swift
y: visible.midY - (contentSize.height + titleBar) / 2    // ← 부호가 반대
```

테스트가 28pt 어긋남을 잡았다 (383.5 vs 397.5).

```
frame = [y - titleBar, y + contentH]        (제목바가 위쪽)
frame.midY = y + (contentH - titleBar) / 2
  이것이 visible.midY 가 되려면
  y = visible.midY - (contentH - titleBar) / 2      ← 빼야 한다
```

**부호를 반대로 적으면 창이 아래로 처져 보인다.** 화면이 1130pt 라 14pt 는 눈에
거의 안 띄지만, **"가운데" 라는 말은 어긋난 자리 가운데가 아니다.**
어긋난 걸 모르고 "가운데로 했다"고 적어두는 게 더 나쁘다.

| 시나리오 | 결과 |

## 6. 교훈

- **진단이 "계산"을 검사하는 것과 "결과"를 검사하는 것은 다르다.** 첫 판은
  순수 함수 `resolve` 의 반환값만 봤다. 순수 함수를 테스트로 100% 고정해도
  **그 값을 창에 넣는 코드가 틀리면 아무 도움이 없다.**
  → **진단은 반드시 "실제 대상을 조작하고 그 상태를 읽어야" 한다.**
- **좌표는 눈으로 확인하면 안 된다.** 사용자가 "왼쪽 하단"이라고 말한 건 정확했고
  `(0, -28)` 이었다. 눈에 띄면 이미 늦은 거고, **안 보이는 14pt 를 잡는 건 숫자로만 가능하다.**
- **`UserDefaults` 값은 그대로 두고 재현 시나리오를 따로 만든다.** 이번엔
  저장값을 백업·삭제하고 **빈 상태로 첫 실행을 재현**했다. 진단이 배치를
  바꾸면 안 된다는 원칙은 그대로 지켰다.
